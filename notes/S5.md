# SOLID

Los 5 principios S.O.L.I.D. de diseño de software son:

S – Single Responsibility Principle (SRP)
O – Open/Closed Principle (OCP)
L – Liskov Substitution Principle (LSP)
I – Interface Segregation Principle (ISP)
D – Dependency Inversion Principle (DIP)

=========================================

*** Violaciones SRP ***
- Clases, modulos muy genericos: service, module, etc
- cambios en el codigo afectan clase o modulo
- la clase involucra varias capas: muchas responsabilidades
- numero elevado de importaciones de clases
- cantidad elevada de metodos public: hace muchas cosas
- muchas lineas de codigo

### OCP - Principio abierto y cerrado

Clases, metodos, modulos - abiertas para extension, cerradas para modificacion

Escribir hola -> Escribir adios
Una funcion abierta para lo mismo, pero cerrada a modificar

### Ejemplo OCP

abierto extension - cerrado modificacion

OJO:
- tmb evitar fiuertes dependencias con codigo de tercero, no podemos contrlar
- si el dia de manana queremos cambiar dependencias, seria un rollo

Por tanto:
- en una sola clase, colocar el get, asi evitamos estar repetirlo en varios lados
- ademas que si necesitamos un cambio, solo se modifica aqui (tolerante al cambio)
    export class HttpClient {
        async get(url: string) {
            const { data, status } = await axios.get(url);
            return { data, status };
        }

- Si removemos axios, solo se afecta esta clase

- inyectamos dependencia de clase y la usamos
    export class TodoService { 
        constructor(private httpClient: HttpClient) {}

### Detectar violaciones OCP
- cambios afectan clase o modulo
- clase o mdulo afecta muchas capas - muchas responsabilidades

Siendo U subtipo de T, cualquier instancia de T deberia ser sutituida por cualquier instancia de U sin alterar sistema

### DI - Principio de inversion de dependencias
Los modulos de alto nivel no depende de bajo nivel
- frontend no dictar reglas de negocio, es el backend
Ambos deberian depender de abstracciones 
Abstracciones no deben depender de concreciones
Los detalles deben depender de abstracciones

* Componentes importantes - capa de dpmionio del negocio
* Menos importantes - UI, persistencia, comunicacion con API

Capas separadas para en caso de cambios, no afectan otros modulos
Si un cambio afecta otros, viola principio

`Depender de abstracciones`
Un modulo depende de otro para su trabajo
- Inyeccion de dependencias

OJO
no se inician modulos en init, constructores => ❌
    constructor() {
        this.service = new Service();
    }
se inyectan dependencias => ✅
    constructor(service: Service) {
        this.service = service;
    }
